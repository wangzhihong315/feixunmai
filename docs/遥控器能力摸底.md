## 1.5 端到端基准（E0 已验证，2026-10-28 02:48 /tmp/take5.wav）

**结论：遥控器语音硬件与解码链路完全正常。** 用 CLI 原型（phicomm-mic，
不经斐讯麦 app 的任何新代码）连接遥控器：按住语音键说话 5 秒——

- 用户耳机实时听到自己的声音（CLI 实时监听输出）；
- 录音文件 3.3 s、mean -33 dB / max -13.8 dB（有正常语音电平）；
- 全程在 HID 配对状态下，语音与 HID 共存无冲突。

⇒ 凡是「豆包听不到声音」类问题，都出在 app 的**输出路由**（AudioSink 设备选择
与切换），不在遥控器/解码。app 侧已确认：diag 日志显示音频包持续到达
（240 采样/包）、门槛通过、按键模拟触发 —— 唯独 sink 指向了错误设备
（日志曾显示 chosen device: iQOO TWS Air3）。

**根因（2026-10-28 03:04 修复，端到端验收通过：QuickTime 电平表动、豆包持续出字）：**

`AudioSink` 原来的顺序是 `connect(mixer→output, format: nil)`（按当时的默认设备
格式接死）→ 再 `AudioUnitSetProperty(CurrentDevice, BlackHole)`。切换设备后
连接里的格式还是旧设备的，引擎照常 running 但**输出静音**（系统设置输入电平表
不渲染虚拟设备，QuickTime 电平表才可靠）。

修复 = 照抄 remote-mic-app `AudioOutput.swift` 的做法：
1. 只 `connect(player→mixer, sourceFormat)`，**不手动连 mixer→output**；
2. **先选设备**（选失败直接抛错），再 `prepare()`/`start()`；
3. 补 `ensureAudible`：对虚拟声卡强制解除静音、音量拉满（对齐它的
   `ensureVirtualAudioDeviceAudible`）。

另一个被排除的干扰项：系统默认输入设备曾是 iQOO 耳机麦，跟随默认输入的应用
听到的是房间环境音。已建议用户把默认输入固定为 BlackHole 2ch。

## 2. 语音键时间线（E1/E2 已验证，2026-10-28 /tmp/probe.log）

**E1 快速点按 ×3**（每下约 0.15–0.23 s）——以第一下为例：

```
[  15.707] HID 0x3e 按下                    ← HID 回声比 GATT 早 14 ms
[  15.721] GATT CTRL 07 fc 01 …             ← 按下即发开始控制包
[  15.765] GATT AUDIO 首包 len=120          ← 音频流 44 ms 后就开始！
[  15.933] GATT CTRL 07 fc 07 …             ← 松开，音频共约 0.2 s
```

三下点按全部有音频流（0.13–0.23 s 的短促流）。**推翻了"点按不推流"的猜想。**

**E2 按住**（实测约 1.7 s）：

```
[  21.175] HID 0x3e 按下
[  21.176] GATT CTRL 07 fc 01 …
（期间持续音频包）
[  22.852] GATT CTRL 07 fc 07 …             ← 松开才发结束包
[  22.929] HID 0x3e 弹起                    ← HID 弹起比 GATT 结束晚 77 ms
```

**E1/E2 结论**：
1. 遥控器按下立刻发 `07 fc 01`，音频流 ~44 ms 后跟上，**点按也推流（短）**；
2. 结束以 `07 fc 07` 为准，音频随松开停止；
3. 所以「点按 → 豆包开始录音但像没声音」的真相是：0.2 s 的音频毛刺触发了
   我们的按键模拟，豆包启动后声音已经停了 —— **该由应用侧过滤短毛刺**，
   而不是等遥控器"长按才推流"（它没有这个机制）。

- [x] 实验 E1：点按 ×3，均有短音频流
- [x] 实验 E2：按住 ~1.7 s，流随松开结束
- [x] 实验 E3（probe2.log）：按住 ~7.9 s —— `07 fc 01`(30.248) → 首音频包 33 ms 后(30.281) →
  全程持续推流 → `07 fc 07`(38.111)，会话干净，速率稳定（约 83 包/秒 → ~20 帧/秒）
- [x] 实验 E4（probe2.log）：松开后 0.9 s 再次按住 3.7 s —— 独立完整的
  start/流/stop，无残留状态，连续说话无衔接问题
- [x] 实验 E6（probe2.log 65.505–65.720）：快速点按 215 ms —— 短流；
  app 侧门槛（0.4 s）应丢弃、豆包无反应（用户已实测确认）

## 4. 结论驱动的设计决策（随实验更新）

1. 按键模拟挂在**音频流**上，并加**最短流时长门槛**（暂定 0.4 s，可调）：
   音频流持续超过门槛才模拟按下；短于门槛的点按/毛刺直接忽略。
   （依据 E1：点按也有 0.2 s 流，所以"首帧即触发"会误触发豆包。）
2. 流结束（`07 fc 07` 或静音超时）后延迟约 0.35 s（排空）再发松开/第二次点按。
   （对齐 remote-mic-app VoiceFnTapSessionController 的 draining 设计。）
3. 语音键 F5 回声必须吞掉（kc=96），开关默认开（依据 §3 + watch 日志）。
4. 统计（次数/时长）只计入超过门槛的真实会话。
